## SQL in Detail - DDL

SQL can generally be divided into four categories: DDL (Data Definition Language), DML (Data Manipulation Language), DCL (Data Control Language), and TCL (Transaction Control Language). DDL is primarily used to create, delete, and modify objects in a database, such as creating, deleting, and modifying two-dimensional tables. Its core keywords include `create`, `drop`, and `alter`. DML is responsible for inserting, deleting, updating, and querying data, with keywords including `insert`, `delete`, `update`, and `select`. DCL is used to grant and revoke permissions, with core keywords `grant` and `revoke`. TCL is typically used for transaction control.

> **Note**: SQL is a case-insensitive language. Generally, we recommend writing keywords in uppercase and other parts in lowercase. If your company's SQL coding standards have mandatory requirements, then follow the company's requirements. Personal preferences should not override company coding standards - this should be common sense for professionals.

### Creating Databases and Tables

Below we will implement a database for a very simple school course selection system. We will name the database `school`. The four key entities are college, teacher, student, and course. Students belong to colleges in a many-to-one relationship, because one college can have multiple students, but a student typically belongs to only one college. Similarly, the relationship between teachers and colleges is also many-to-one. A teacher can teach multiple courses, and if each course has only one instructor, then the relationship between courses and teachers is also many-to-one. If multiple teachers are allowed to co-teach a course, then courses and teachers would have a many-to-many relationship. For simplicity, we will design the relationship between courses and teachers as many-to-one. Students and courses have a typical many-to-many relationship, because a student can select multiple courses and a course can be selected by multiple students. Relational databases need an intermediate table to maintain a many-to-many relationship between two entities. In the end, our school course selection system has five tables: the college table (`tb_college`), student table (`tb_student`), teacher table (`tb_teacher`), course table (`tb_course`), and course selection record table (`tb_record`), where the course selection record table is the intermediate table that maintains the many-to-many relationship between students and courses.

```SQL
-- Drop the database named school if it exists
DROP DATABASE IF EXISTS `school`;

-- Create a database named school and set the default character set and collation
CREATE DATABASE `school` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;

-- Switch to the school database context
USE `school`;

-- Create the college table
CREATE TABLE `tb_college`
(
`col_id`    int unsigned AUTO_INCREMENT      COMMENT 'ID',
`col_name`  varchar(50)  NOT NULL            COMMENT 'Name',
`col_intro` varchar(500) NOT NULL DEFAULT '' COMMENT 'Introduction',
PRIMARY KEY (`col_id`)
);

-- Create the student table
CREATE TABLE `tb_student`
(
`stu_id`    int unsigned NOT NULL           COMMENT 'Student ID',
`stu_name`  varchar(20)  NOT NULL           COMMENT 'Name',
`stu_sex`   boolean      NOT NULL DEFAULT 1 COMMENT 'Gender',
`stu_birth` date         NOT NULL           COMMENT 'Date of Birth',
`stu_addr`  varchar(255) DEFAULT ''         COMMENT 'Hometown',
`col_id`    int unsigned NOT NULL           COMMENT 'College ID',
PRIMARY KEY (`stu_id`),
CONSTRAINT `fk_student_col_id` FOREIGN KEY (`col_id`) REFERENCES `tb_college` (`col_id`)
);

-- Create the teacher table
CREATE TABLE `tb_teacher`
(
`tea_id`    int unsigned NOT NULL                COMMENT 'Employee ID',
`tea_name`  varchar(20)  NOT NULL                COMMENT 'Name',
`tea_title` varchar(10)  NOT NULL DEFAULT '助教' COMMENT 'Title',
`col_id`    int unsigned NOT NULL                COMMENT 'College ID',
PRIMARY KEY (`tea_id`),
CONSTRAINT `fk_teacher_col_id` FOREIGN KEY (`col_id`) REFERENCES `tb_college` (`col_id`)
);

-- Create the course table
CREATE TABLE `tb_course`
(
`cou_id`     int unsigned NOT NULL COMMENT 'ID',
`cou_name`   varchar(50)  NOT NULL COMMENT 'Name',
`cou_credit` int          NOT NULL COMMENT 'Credits',
`tea_id`     int unsigned NOT NULL COMMENT 'Instructor',
PRIMARY KEY (`cou_id`),
CONSTRAINT `fk_course_tea_id` FOREIGN KEY (`tea_id`) REFERENCES `tb_teacher` (`tea_id`)
);

-- Create the course selection record table
CREATE TABLE `tb_record`
(
`rec_id`   bigint unsigned AUTO_INCREMENT COMMENT 'Record ID',
`stu_id`   int unsigned    NOT NULL       COMMENT 'Student ID',
`cou_id`   int unsigned    NOT NULL       COMMENT 'Course ID',
`sel_date` date            NOT NULL       COMMENT 'Selection Date',
`score`    decimal(4,1)                   COMMENT 'Exam Score',
PRIMARY KEY (`rec_id`),
CONSTRAINT `fk_record_stu_id` FOREIGN KEY (`stu_id`) REFERENCES `tb_student` (`stu_id`),
CONSTRAINT `fk_record_cou_id` FOREIGN KEY (`cou_id`) REFERENCES `tb_course` (`cou_id`),
CONSTRAINT `uk_record_stu_cou` UNIQUE (`stu_id`, `cou_id`)
);
```

- When creating and deleting databases, the keyword `database` can also be replaced with `schema`; both have the same effect.

- In the CREATE TABLE statement, `not null` is a NOT NULL constraint that requires a field to have a value; `default` is used to specify a default value for a field, known as a default value constraint; `primary key` is a primary key constraint that designates a column capable of uniquely identifying a record, ensuring that each record is unique since primary keys do not allow duplicates; `foreign key` is a foreign key constraint that maintains referential integrity between two tables. For example, since the col_id field in the student table has a foreign key constraint requiring it to reference (`references`) the col_id in the college table, the college ID in the student table must come from the college IDs in the college table and cannot be assigned arbitrary values. If you need to name the primary key constraint, foreign key constraint, etc., you can use the `constraint` keyword followed by the constraint name.

- The `comment` keyword in the CREATE TABLE statement is used to add comments to columns and tables, enhancing code readability and maintainability.

- When creating a table, you can choose the underlying storage engine. MySQL supports multiple storage engines, which can be viewed using the `show engines` command. Versions of MySQL after 5.5 use InnoDB as the default storage engine, which we recommend (because it is better suited for modern internet applications' requirements for high concurrency, performance, and transaction support). For backward compatibility of SQL statements, we can specify the InnoDB storage engine by adding `engine=innodb` after the closing parenthesis of the CREATE TABLE statement.

  Regarding data type selection: VARCHAR and CHAR are the two types commonly used for storing string data. The former is usually called a variable-length string, while the latter is called a fixed-length string. For the InnoDB storage engine, the row storage format does not differentiate between fixed-length and variable-length columns, so there is no essential difference between VARCHAR and CHAR, and the latter is not necessarily faster than the former. If you need to store very large strings, you can use the TEXT type; if you need to store very large byte strings, you can use the BLOB (Binary Large Object) type. In MySQL, TEXT and BLOB each include three different types: TEXT, MEDIUMTEXT, LONGTEXT and BLOB, MEDIUMBLOB, LONGBLOB. The main difference between them is the maximum size of data they can store. For floating-point numbers, you can use FLOAT or DOUBLE types. FLOAT is no longer recommended and may be removed in future versions of MySQL. For fixed-point numbers, you should use the DECIMAL type, which allows you to specify the number of significant digits before and after the decimal point. For storing dates and times, the DATETIME type is preferred over the TIMESTAMP type because the former can represent a larger range of dates and times. The latter is essentially an integer under the hood that records the number of milliseconds between the specified date/time and 1970-01-01 00:00:00, and will overflow after 2038-01-19 03:14:07.

  For auto-increment fields (AUTO_INCREMENT), if you are using MySQL 5.x, be aware of the auto-increment value rollback issue. This issue has been well resolved in MySQL 8.x, which also has many other improvements in both functionality and performance. Therefore, we strongly recommend using MySQL 8.x. In high-concurrency database access scenarios, AUTO_INCREMENT not only has performance issues but may also produce duplicate ID values in multi-machine architectures. In such scenarios, using distributed ID generation algorithms (SnowFlake, TinyID, etc.) is the best choice. Interested readers can explore this on their own.

### Dropping and Altering Tables

Using the student table as an example, let us explain how to drop and alter tables. To drop a table, you can use `drop table`, as shown below.

```SQL
DROP TABLE `tb_student`;
```

Or

```SQL
DROP TABLE IF EXISTS `tb_student`;
```

Note that if the student table already has data and that data is referenced by other tables, then the student table cannot be dropped, and the above operation will produce an error. In the next lesson, we will explain how to insert data into tables, and you can try to see whether you can successfully drop the student table.

To alter the student table, you can use `alter table`, which can be broken down into the following cases:

Alter a table to add a new column. For example, add a phone number column to the student table.

```SQL
ALTER TABLE `tb_student` ADD COLUMN `stu_tel` varchar(20) NOT NULL COMMENT 'Phone Number';
```

> **Note**: If a NOT NULL constraint (`not null`) is specified when adding a new column, the student table must not have any existing data. Otherwise, the existing data would have no value for the stu_tel column after it is added, which would violate the NOT NULL constraint. Of course, we can also use a default value constraint when adding the column to solve this problem.

Alter a table to drop a specified column. For example, drop the phone number column that was just added.

```SQL
ALTER TABLE `tb_student` DROP COLUMN `stu_tel`;
```

Alter a table to modify a column's data type. For example, change stu_sex in the student table to a character type.

```SQL
ALTER TABLE `tb_student` MODIFY COLUMN `stu_sex` char(1) NOT NULL DEFAULT 'M' COMMENT 'Gender';
```

Alter a table to rename a column. For example, rename stu_sex to stu_gender in the student table.

```SQL
ALTER TABLE `tb_student` CHANGE COLUMN `stu_sex` `stu_gender` boolean DEFAULT 1 COMMENT 'Gender';
```

Alter a table to drop a constraint. For example, drop the foreign key constraint on the col_id column of the student table.

```SQL
ALTER TABLE `tb_student` DROP FOREIGN KEY `fk_student_col_id`;
```

Alter a table to add a constraint. For example, add a foreign key constraint to the col_id column of the student table.

```SQL
ALTER TABLE `tb_student` ADD FOREIGN KEY (`col_id`) REFERENCES `tb_college` (`col_id`);
```

Or

```SQL
ALTER TABLE `tb_student` ADD CONSTRAINT `fk_student_col_id` FOREIGN KEY (`col_id`) REFERENCES `tb_college` (`col_id`);
```

> **Note**: When adding a foreign key constraint, you can also specify what should happen when the referenced table undergoes delete and update operations using `on update` and `on delete`. The default value for both is `restrict`, which means that if a foreign key constraint exists, updates and deletes of the referenced data are not allowed. Besides `restrict`, possible values here include `cascade` (cascading operation) and `set null` (set to null). Interested readers can explore this on their own.

Rename a table. For example, rename the student table to tb_stu_info.

```SQL
ALTER TABLE `tb_student` RENAME TO `tb_stu_info`;
```

> **Tip**: In general, do not casually rename databases or tables.
