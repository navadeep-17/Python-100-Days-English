### Views

A view is an object in a relational database that combines a set of query instructions into a queryable result set organized as a data table. In simple terms, a view is a virtual table. Unlike data tables, a data table is a physical structure, while a view is a virtual structure. You can also think of a view as a named SQL statement saved in the database.

Using views provides the following benefits:

1. Physical data tables can be hidden from external programs, preventing them from knowing the actual data structure. This allows users to access only parts of a table rather than the entire table, reducing the risk of database attacks.
2. In most cases, views are read-only (updating views typically has many restrictions), so external programs cannot directly modify data through views.
3. SQL statements can be reused. Highly complex queries can be wrapped in a view table, and the required data can be retrieved by directly accessing the view. Views can also be treated as data tables for join queries.
4. Views can return data in a different format from the physical data tables. Data can be formatted when creating the view.

Creating a view.

```SQL
create view `vw_emp_simple`
as
select  `eno`,
        `ename`,
        `job`,
        `dno`
  from  `tb_emp`;
```

> **Tip**: Because views do not contain data, the query must be executed each time the view is used to obtain data. If you create a complex view using join queries or nested queries, you may find that query performance degrades significantly. Therefore, before using complex views, you should test to ensure their performance meets the application's requirements.

With the view above, we can use the DCL discussed earlier to restrict certain users to only retrieve employee information from the view. This way, sensitive fields such as salary (`sal`) and allowance (`comm`) in the employee table will not be exposed to users. The code below demonstrates how to retrieve data from the view.

```SQL
select * from `vw_emp_simple`;
```

Since a view is a virtual table, can the data in a view be updated? The updatability of a view depends on the specific situation. The following types of views cannot be updated:

1. Views that use aggregate functions (`SUM`, `MIN`, `MAX`, `AVG`, `COUNT`, etc.), `DISTINCT`, `GROUP BY`, `HAVING`, `UNION`, or `UNION ALL`.
2. Views where the `SELECT` contains subqueries.
3. Views whose `FROM` clause contains a non-updatable view.
4. Views where the `WHERE` clause's subquery references a table from the `FROM` clause.

Dropping a view.

```SQL
drop view if exists `vw_emp_simple`;
```

> **Note**: If you want to update a view, you can first drop it using the command above, or use `create or replace view` to update it.

Rules and restrictions for views.

1. Views can be nested. You can construct a new view using data retrieved from other views. Views can also be used together with tables.
2. An `order by` clause can be used when creating a view, but if an `order by` is also used when retrieving data from the view, the original `order by` in the view will be overridden.
3. Views cannot use indexes and will not trigger the execution of triggers (in practice, triggers are generally not recommended due to performance considerations, so we will not introduce this concept).

### Functions

Functions in MySQL are quite similar to functions in Python, because functions are used to encapsulate relatively independent and reusable pieces of code. If we must find some differences, MySQL functions can execute SQL statements. In the example below, we implement a custom function to truncate strings that exceed a certain length.

```SQL
delimiter $$

create function fn_truncate_string(
    content varchar(10000),
    max_length int unsigned
) returns varchar(10000) no sql
begin
    declare result varchar(10000) default content;
    if char_length(content) > max_length then
        set result = left(content, max_length);
        set result = concat(result, '……');
    end if;
    return result;
end $$

delimiter ;
```

> **Note 1**: The `no sql` after the function declaration states that the function body does not use SQL statements. If the function body needs to read data via SQL, it should be declared as `reads sql data`.
>
> **Note 2**: The `delimiter` commands before and after the function definition are used to change the terminator (delimiter). Since statements within the function body end with `;`, if we do not redefine the delimiter, the code will be truncated and executed when a `;` is encountered, which is obviously not what we want.

Calling the custom function in a query.

```SQL
select fn_truncate_string('和我在成都的街头走一走，直到所有的灯都熄灭了也不停留', 10) as short_string;
```

```

+--------------------------------------+
| 和我在成都的街头走一……                 |
+--------------------------------------+
```

### Procedures

A procedure (also called a stored procedure) is a pre-compiled collection of SQL statements stored in the database. Calling procedures can simplify the work of application developers, reduce communication with the database server, and help improve data operation performance. In fact, up to now, the SQL statements we have used are single statements targeting one or more tables. However, in actual development, it is common to encounter situations where an operation requires multiple SQL statements. For example, when an e-commerce website processes a user order, it needs to perform the following series of actions:

1. Check inventory to verify whether the corresponding items exist and whether stock is sufficient.
2. If items are in stock, lock the inventory to ensure these items are not sold to others, and reduce the available quantity to reflect the correct inventory level.
3. If stock is insufficient, further interaction with suppliers may be needed, or at least a system notification should be generated.
4. Regardless of whether the order is successfully processed, transaction records need to be generated, and a notification message needs to be sent to the corresponding user.

We can encapsulate complex operations within procedures. This not only helps ensure data consistency but also means that if the business changes in the future, only the procedure needs to be adjusted and modified. For the users calling the procedure, the procedure does not expose the details of the data tables, and executing a procedure is much faster than executing a set of SQL statements one by one.

The following procedure implements a general salary increase for employees in the hrs database. The specific rules are: employees in department `10` get a raise of `300`, employees in department `20` get a raise of `800`, and employees in department `30` get a raise of `500`.

```SQL
delimiter $$

create procedure sp_upgrade_salary()
begin
    declare flag boolean default 1;
    -- Define an exception handler
    declare continue handler for sqlexception set flag=0;

    -- Start transaction
    start transaction;

    update tb_emp set sal=sal+300 where dno=10;
    update tb_emp set sal=sal+800 where dno=20;
    update tb_emp set sal=sal+500 where dno=30;

    -- Commit or rollback transaction
    if flag then
        commit;
    else
        rollback;
    end if;
end $$

delimiter ;
```

> **Note**: The procedure code above uses `start transaction` to begin a transaction. Transactions are briefly introduced at the end of this lesson. To determine whether an exception occurred in the code and thus decide whether to commit or rollback the transaction, the procedure defines a variable named `flag` and an exception handler. If an exception occurs, `flag` will be set to `0`, and the subsequent branch structure will decide whether to execute `commit` or `rollback` based on the value of `flag`.

Calling a procedure.

```SQL
call sp_upgrade_salary();
```

Dropping a procedure.

```SQL
drop procedure if exists sp_upgrade_salary;
```

In procedures, we can define variables and conditions, use branching and looping statements, operate on query results through cursors, and use event schedulers. These topics will not be covered here for now. Although we have mentioned many benefits of procedures, in actual development, if procedures are used frequently and a large amount of complex computation is placed in procedures, this will put enormous pressure on the database server. The database is often the performance bottleneck, and using procedures only makes things worse. Therefore, for internet product development, we generally recommend letting the database focus on storage while leaving complex computation and processing to programs on application servers. If the application server becomes overwhelmed, it is relatively easy to deploy multiple application servers to distribute the load.

### Other Topics

#### Normalization Theory

Normalization theory provides the guiding principles for designing two-dimensional tables in relational databases.

1. First Normal Form: The value domain of every column in a data table consists of atomic values that cannot be further divided.
2. Second Normal Form: All data in a data table must be fully dependent on the table's keys (primary keys and candidate keys).
3. Third Normal Form: All non-key attributes are only related to candidate keys, meaning non-key attributes should be independent of each other.

> **Note**: In practice, for efficiency considerations, we may intentionally create anti-normalization designs when designing tables, deliberately lowering the normalization level and adding redundant data to achieve better operational performance.

#### Data Integrity

1. Entity Integrity - Every entity is unique

   - Primary key (`primary key`) / Unique constraint (`unique`)
2. Referential Integrity - Relationships do not allow references to non-existent entities

   - Foreign key (`foreign key`)
3. Domain Integrity - Data is valid
   - Data types and lengths

   - NOT NULL constraint (`not null`)

   - Default value constraint (`default`)

   - Check constraint (`check`)

     > **Note**: Before MySQL 8.x, the check constraint did not actually work.

#### Data Consistency

1. Transaction: A series of read/write operations on a database. These operations either all succeed or all fail.

2. ACID Properties of Transactions
   - Atomicity: A transaction is executed as a whole. The database operations contained within it are either all executed or none are executed.
   - Consistency: A transaction should ensure that the database transitions from one consistent state to another consistent state.
   - Isolation: When multiple transactions execute concurrently, the execution of one transaction should not affect the execution of other transactions.
   - Durability: Modifications to the database by a committed transaction should be permanently saved in the database.

3. Transaction Operations in MySQL

   - Start a transaction

     ```SQL
     start transaction
     ```

   - Commit a transaction

     ```SQL
     commit
     ```

   - Rollback a transaction

     ```SQL
     rollback
     ```

4. View the transaction isolation level

    ```SQL
    show variables like 'transaction_isolation';

    ```
    +-----------------------+-----------------+

Transactions in relational databases are a large topic, because when multiple concurrent transactions access data, three types of read problems (dirty reads, non-repeatable reads, phantom reads) and two types of update problems (first lost update, second lost update) can occur. If you want to learn about these five types of problems, you can read question #80 in the article [*Complete Collection of Java Interview Questions (Part 1)*](https://blog.csdn.net/jackfrued/article/details/44921941) published on the CSDN website. To avoid these problems, relational databases have corresponding locking mechanisms at the bottom level, which can be classified by lock target into table-level locks and row-level locks, and by concurrent transaction locking relationship into shared locks and exclusive locks. However, using locks directly is very cumbersome, so databases provide automatic locking mechanisms for users. As long as users specify the appropriate transaction isolation level, the database will analyze SQL statements and apply appropriate locks to the resources accessed by transactions. Additionally, databases maintain these locks and improve system performance through various means, all of which is transparent to users. To learn about the details of MySQL transactions and locks, we recommend reading the advanced book [*High Performance MySQL*](https://item.jd.com/11220393.html), which is a classic book in the database field.
