## Indexes

Indexes are the most important means of improving query performance in relational databases. An index in a relational database is like the table of contents of a book. Imagine trying to find a specific topic in a book without a table of contents - that would be terrible! You would have to flip through page by page to determine where that topic is located. Although creating indexes comes with storage space overhead, just like a book's table of contents takes up some pages, the reduction in query time gained by sacrificing space is also very significant.

All data types in a MySQL database can be indexed. For the InnoDB storage engine in MySQL 8.0, it supports three types of indexes: B+ tree indexes, full-text indexes, and R-tree indexes. Here, we will only introduce the most widely used B+ tree index. The reason for using B+ trees is very simple: they are currently the most efficient data structure for disk-based massive data storage and sorting. A B+ tree is a [balanced tree](https://zh.wikipedia.org/zh-cn/%E5%B9%B3%E8%A1%A1%E6%A0%91), typically with a height of 3 or 4, yet it can store data ranging from millions to billions of records. Querying a single record from this data requires only 3 or 4 I/O operations.

A B+ tree consists of root nodes, intermediate nodes, and leaf nodes, where leaf nodes store the sorted data. Since records are sorted on the index, a binary search can be used to find data within a leaf node, which is a very efficient search method. When there is very little data, the B+ tree has only a root node, and data is stored on the root node. As more records are added, the B+ tree splits. The root node no longer stores data but instead provides pointers to access the next level of nodes, helping to quickly determine which leaf node contains the data.

When creating a two-dimensional table, we typically specify a primary key column for the table. An index is created by default on the primary key column. For MySQL's InnoDB storage engine, because it uses an index-organized table data storage structure, the index on the primary key is the entire table's data. This type of index is called a **clustered index**. Obviously, a table can only have one clustered index, otherwise the table data would need to be stored multiple times. Indexes that we create ourselves are secondary indexes, more commonly called **non-clustered indexes**. Through custom non-clustered indexes, we can only locate a record's primary key. When fetching data, we may need to perform another query through the clustered index on the primary key. This phenomenon is called "bookmark lookup" (or "table access by index rowid"), which is why retrieving data through non-clustered indexes is typically slower than using clustered indexes.

Next, let us illustrate the significance of indexes with a simple example. Suppose we want to search for students by their name - this is a scenario commonly encountered in actual development, similar to searching for products by product name. We can use MySQL's `explain` keyword to view the execution plan of a SQL statement (the specific steps the database takes to execute a SQL statement).

```SQL
explain select * from tb_student where stuname='林震南'\G
```

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: tb_student
   partitions: NULL
         type: ALL
possible_keys: NULL
          key: NULL
      key_len: NULL
          ref: NULL
         rows: 11
     filtered: 10.00
        Extra: Using where
1 row in set, 1 warning (0.00 sec)
```

In the SQL execution plan above, several items are worth our attention:

1. `select_type`: The type of query.
    - `SIMPLE`: Simple SELECT, does not use UNION operations or subqueries.
    - `PRIMARY`: If the query contains subqueries, the outermost SELECT is marked as PRIMARY.
    - `UNION`: The second or subsequent SELECT statement in a UNION operation.
    - `SUBQUERY`: The first SELECT in a subquery.
    - `DERIVED`: SELECT subquery of a derived table.
2. `table`: The table corresponding to the query.
3. `type`: The method MySQL uses to find rows that satisfy the conditions in the table, also called the access type. These include: `ALL` (full table scan), `index` (full index scan, only traverses the index tree), `range` (index range scan), `ref` (non-unique index scan), `eq_ref` (unique index scan), `const` / `system` (constant-level query), `NULL` (no need to access the table or index). Among all access types, ALL clearly has the worst performance as it represents a full table scan that must examine every row in the table to find matching rows.
4. `possible_keys`: Indexes that MySQL could choose, but **may not actually use**.
5. `key`: The index MySQL actually uses. If `NULL`, no index was used.
6. `key_len`: The length of the index used. A shorter length is better when it does not affect the query.
7. `rows`: The number of rows that need to be scanned to execute the query. This is an **estimated value**.
8. `extra`: Additional information about the query.
    - `Using filesort`: MySQL cannot use an index to complete the sort operation.
    - `Using index`: Only the index information is needed without further table lookup.
    - `Using temporary`: MySQL needs to use a temporary table to store the result set, commonly used for grouping and sorting.
    - `Impossible where`: The `where` clause results in no rows meeting the conditions.
    - `Distinct`: MySQL stops searching for more rows for the current row combination after finding the first match.
    - `Using where`: The queried columns are not covered by the index, and the filter condition is not a leading column of the index.

From the execution plan above, we can see that when we search for a student by name, a full table scan is actually performed. Needless to say, the query performance is definitely very poor, especially when the table has many rows. If we frequently search for students by name, we should create an index on the student name column to speed up the query.

```SQL
create index idx_student_name on tb_student(stuname);
```

Let us check the execution plan again for the same SQL.

```SQL
explain select * from tb_student where stuname='林震南'\G
```

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: tb_student
   partitions: NULL
         type: ref
possible_keys: idx_student_name
          key: idx_student_name
      key_len: 62
          ref: const
         rows: 1
     filtered: 100.00
        Extra: NULL
1 row in set, 1 warning (0.00 sec)
```

Notice that after creating an index on the student name, the query is no longer a full table scan but an index-based query, and the number of rows scanned is just one. This clearly greatly improves query performance. MySQL also allows creating prefix indexes, which means creating an index on the first N characters of an index field. This can reduce the space occupied by the index (but saving space may waste time - **time and space are an irreconcilable trade-off**), as shown below.

```SQL
create index idx_student_name_1 on tb_student(stuname(1));
```

The index above is essentially created based on the first character of the student's name. Let us look at the SQL execution plan again.

```SQL
explain select * from tb_student where stuname='林震南'\G
```

```
*************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: tb_student
   partitions: NULL
         type: ref
possible_keys: idx_student_name
          key: idx_student_name
      key_len: 5
          ref: const
         rows: 2
     filtered: 100.00
        Extra: Using where
1 row in set, 1 warning (0.00 sec)
```

Notice that this time the number of scanned rows has become 2, because there are two students with the surname "林" in the student table. When we only use the first character of the name as the index, the query through the index will find both rows.

To drop an index, you can use the following SQL.

```SQL
alter table tb_student drop index idx_student_name;
```

Or

```SQL
drop index idx_student_name on tb_student;
```

When creating indexes, we can also use composite indexes and function indexes (supported since MySQL 5.7). Using composite indexes effectively for **index covering** can reduce unnecessary sorting and bookmark lookups, which can multiply query performance. Interested readers can explore this on their own.

Let us briefly summarize the principles for index design:

1. The columns **most suitable** for indexing are those appearing in **WHERE clauses** and join clauses.
2. The greater the cardinality of an indexed column (more distinct values, fewer duplicates), the better the index works.
3. Using **prefix indexes** can reduce the space occupied by indexes, allowing more indexes to be cached in memory.
4. **More indexes are not always better**. While indexes speed up read operations (queries), they slow down write operations (insert, delete, update) because data changes require index updates, just like adding or removing chapters in a book requires updating the table of contents.
5. When using the InnoDB storage engine, regular indexes on a table store the primary key value, so **choose shorter data types for primary keys** whenever possible. This can effectively reduce the space occupied by indexes and improve index caching efficiency.

Finally, one more point needs to be mentioned. For B-tree indexes used by InnoDB, in addition to equality comparisons, the index is also effective when using `>`, `<`, `>=`, `<=`, `BETWEEN...AND...`, `<>` with numeric columns. For string columns, if using a fuzzy query that does not start with a wildcard, the index is also effective. However, other situations will cause the index to fail, meaning a full table scan will likely be performed.
