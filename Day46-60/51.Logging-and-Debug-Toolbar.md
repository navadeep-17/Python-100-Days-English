## Logging and Debug Toolbar

### Configuring Logging

During the project development phase, displaying sufficient debug information to assist developers in debugging code is very necessary. After the project goes live, recording warnings, errors, and other information that occur during system runtime for relevant personnel to understand the system's operational status and maintain code is also essential. At the same time, collecting log data also lays a foundation for digital operations of the website. Through analysis of system runtime logs, we can monitor website traffic and its distribution, and also mine user habits and behavioral patterns.

Next, let's first look at how to configure logging through Django's configuration file. Django's logging configuration can basically follow the official documentation combined with the actual project requirements. This content can largely be copied from the official documentation and then adjusted locally. Below are some reference configurations.

```Python
LOGGING = {
    'version': 1,
    # Whether to disable existing loggers
    'disable_existing_loggers': False,
    # Log formatters
    'formatters': {
        'simple': {
            'format': '%(asctime)s %(module)s.%(funcName)s: %(message)s',
            'datefmt': '%Y-%m-%d %H:%M:%S',
        },
        'verbose': {
            'format': '%(asctime)s %(levelname)s [%(process)d-%(threadName)s] '
                      '%(module)s.%(funcName)s line %(lineno)d: %(message)s',
            'datefmt': '%Y-%m-%d %H:%M:%S',
        }
    },
    # Log filters
    'filters': {
        # Only active when DEBUG is True in Django configuration
        'require_debug_true': {
            '()': 'django.utils.log.RequireDebugTrue',
        },
    },
    # Log handlers
    'handlers': {
        # Output to console
        'console': {
            'class': 'logging.StreamHandler',
            'level': 'DEBUG',
            'filters': ['require_debug_true'],
            'formatter': 'simple',
        },
        # Output to file (rotated weekly)
        'file1': {
            'class': 'logging.handlers.TimedRotatingFileHandler',
            'filename': 'access.log',
            'when': 'W0',
            'backupCount': 12,
            'formatter': 'simple',
            'level': 'INFO',
        },
        # Output to file (rotated daily)
        'file2': {
            'class': 'logging.handlers.TimedRotatingFileHandler',
            'filename': 'error.log',
            'when': 'D',
            'backupCount': 31,
            'formatter': 'verbose',
            'level': 'WARNING',
        },
    },
    # Loggers
    'loggers': {
        'django': {
            # Log handlers to use
            'handlers': ['console', 'file1', 'file2'],
            # Whether to propagate log information upward
            'propagate': True,
            # Log level (not necessarily the final log level)
            'level': 'DEBUG',
        },
    }
}
```

You may have noticed that the `formatters` in the logging configuration above are **log formatters**, which define how to format log output. The format placeholders represent:

1. `%(name)s` - Logger name
2. `%(levelno)s` - Numeric log level
3. `%(levelname)s` - Text name of the log level
4. `%(filename)s` - Filename of the source file that made the logging call
5. `%(pathname)s` - Pathname of the source file that made the logging call
6. `%(funcName)s` - Function name that made the logging call
7. `%(module)s` - Module name that made the logging call
8. `%(lineno)s` - Line number where the logging call was made
9. `%(created)s` - Time when the log record was created
10. `%(asctime)s` - Date and time
11. `%(msecs)s` - Millisecond portion
12. `%(thread)d` - Thread ID (integer)
13. `%(threadName)s` - Thread name
14. `%(process)d` - Process ID (integer)

The handlers in the logging configuration specify **log handlers** - simply put, they specify whether to output logs to the console, a file, or a server on the network. Available handlers include:

1. `logging.StreamHandler(stream=None)` - Can output information to file-like objects such as `sys.stdout` or `sys.stderr`
2. `logging.FileHandler(filename, mode='a', encoding=None, delay=False)` - Writes log messages to a file
3. `logging.handlers.DatagramHandler(host, port)` - Sends log information to a network host at the specified address and port using the UDP protocol
4. `logging.handlers.HTTPHandler(host, url)` - Uploads log messages to an HTTP server using HTTP GET or POST methods
5. `logging.handlers.RotatingFileHandler(filename, mode='a', maxBytes=0, backupCount=0, encoding=None, delay=False)` - Writes log messages to a file; if the file size exceeds the value specified by `maxBytes`, a new file is generated to record logs
6. `logging.handlers.SocketHandler(host, port)` - Sends log information to a network host at the specified address and port using the TCP protocol
7. `logging.handlers.SMTPHandler(mailhost, fromaddr, toaddrs, subject, credentials=None, secure=None, timeout=1.0)` - Outputs logs to a specified email address
8. `logging.MemoryHandler(capacity, flushLevel=ERROR, target=None, flushOnClose=True)` - Outputs logs to a specified buffer in memory

Each log handler above specifies a `level` attribute, which represents the log level. Different log levels reflect the severity of information recorded in the logs. Python defines six log levels, in order from lowest to highest: NOTSET, DEBUG, INFO, WARNING, ERROR, CRITICAL.

The **loggers** configured last are what actually output the logs. The Django framework provides the following built-in loggers:

1. `django` - All loggers in the Django hierarchy
2. `django.request` - Log messages related to request handling. 5xx responses are treated as error messages; 4xx responses are treated as warning messages
3. `django.server` - Log messages related to requests received by the server invoked through runserver. 5xx responses are treated as error messages; 4xx responses are logged as warning messages; everything else is logged as INFO
4. `django.template` - Log messages related to template rendering
5. `django.db.backends` - Log messages generated by database interactions. If you want to see the SQL statements executed by the ORM framework, you can use this logger.

The log level configured in the logger may not be the final log level, because the log level configured in the handler also needs to be considered, and the higher of the two is used as the final log level.

### Configuring Django-Debug-Toolbar

If you want to debug your Django project, you absolutely must know about the incredible tool called Django-Debug-Toolbar. It is an essential tool for debugging and optimization during project development. Once configured, you can conveniently view the project runtime information listed in the table below, which is crucial for debugging projects and optimizing web application performance.

| Item        | Description                              |
| ----------- | ---------------------------------------- |
| Versions    | Django version                           |
| Time        | Time spent by the view                   |
| Settings    | Values set in the configuration file     |
| Headers     | HTTP request and response header info    |
| Request     | Various variables and info related to the request |
| StaticFiles | Static file loading status               |
| Templates   | Template-related information             |
| Cache       | Cache usage                              |
| Signals     | Django built-in signal information       |
| Logging     | Recorded log information                 |
| SQL         | SQL statements sent to the database and their execution time |

1. Install Django-Debug-Toolbar.

   ```Shell
   pip install django-debug-toolbar
   ```

2. Configuration - Modify settings.py.

   ```Python
   INSTALLED_APPS = [
       'debug_toolbar',
   ]

   MIDDLEWARE = [
       'debug_toolbar.middleware.DebugToolbarMiddleware',
   ]

   DEBUG_TOOLBAR_CONFIG = {
       # Include jQuery library
       'JQUERY_URL': 'https://cdn.bootcss.com/jquery/3.3.1/jquery.min.js',
       # Whether the toolbar is collapsed
       'SHOW_COLLAPSED': True,
       # Whether to show the toolbar
       'SHOW_TOOLBAR_CALLBACK': lambda x: True,
   }
   ```

3. Configuration - Modify urls.py.

   ```Python
   if settings.DEBUG:

       import debug_toolbar

       urlpatterns.insert(0, path('__debug__/', include(debug_toolbar.urls)))
   ```

4. After configuring Django-Debug-Toolbar, you will see a debug toolbar on the right side of the page, as shown in the image below. It contains the various debug information mentioned above, including execution time, project settings, request headers, SQL, static resources, templates, cache, signals, etc., which is very convenient to view.

### Optimizing ORM Code

After configuring logging or Django-Debug-Toolbar, we can check the execution of the view function that exports teacher data to an Excel report. Here we focus on what the SQL queries generated by the ORM framework actually look like - the results here will probably surprise you somewhat. After executing `Teacher.objects.all()`, we can notice that the SQL displayed in the console or output through Django-Debug-Toolbar looks like this:

```SQL
SELECT `tb_teacher`.`no`, `tb_teacher`.`name`, `tb_teacher`.`detail`, `tb_teacher`.`photo`, `tb_teacher`.`good_count`, `tb_teacher`.`bad_count`, `tb_teacher`.`sno` FROM `tb_teacher`; args=()
SELECT `tb_subject`.`no`, `tb_subject`.`name`, `tb_subject`.`intro`, `tb_subject`.`create_date`, `tb_subject`.`is_hot` FROM `tb_subject` WHERE `tb_subject`.`no` = 101; args=(101,)
SELECT `tb_subject`.`no`, `tb_subject`.`name`, `tb_subject`.`intro`, `tb_subject`.`create_date`, `tb_subject`.`is_hot` FROM `tb_subject` WHERE `tb_subject`.`no` = 101; args=(101,)
SELECT `tb_subject`.`no`, `tb_subject`.`name`, `tb_subject`.`intro`, `tb_subject`.`create_date`, `tb_subject`.`is_hot` FROM `tb_subject` WHERE `tb_subject`.`no` = 101; args=(101,)
SELECT `tb_subject`.`no`, `tb_subject`.`name`, `tb_subject`.`intro`, `tb_subject`.`create_date`, `tb_subject`.`is_hot` FROM `tb_subject` WHERE `tb_subject`.`no` = 101; args=(101,)
SELECT `tb_subject`.`no`, `tb_subject`.`name`, `tb_subject`.`intro`, `tb_subject`.`create_date`, `tb_subject`.`is_hot` FROM `tb_subject` WHERE `tb_subject`.`no` = 103; args=(103,)
SELECT `tb_subject`.`no`, `tb_subject`.`name`, `tb_subject`.`intro`, `tb_subject`.`create_date`, `tb_subject`.`is_hot` FROM `tb_subject` WHERE `tb_subject`.`no` = 103; args=(103,)
```

This problem is commonly known as the "1+N query" (some places also call it the "N+1 query"). Originally, fetching teacher data only requires one SQL statement, but because teachers are associated with subjects, when we query `N` teacher records, Django's ORM framework sends `N` additional SQL statements to the database to query the subject information for each teacher. Each SQL execution has significant overhead and puts pressure on the database server. If we could complete the teacher and subject queries in a single SQL statement, that would certainly be a better approach - and it's easy to do. I'm sure you've already figured out how: we can use a join query. But how do we achieve this when using Django's ORM framework? For many-to-one relationships (like teachers and subjects in the voting application), we can use the `QuerySet`'s `select_related()` method to load related objects; for many-to-many relationships (like orders and products in an e-commerce site), we can use `prefetch_related()` to load related objects.

In the view function that exports the teacher Excel report, we can optimize the code as follows.

```Python
queryset = Teacher.objects.all().select_related('subject')
```

In fact, the operation of querying teacher upvote and downvote data in the view function that generates the ECharts frontend report can also be optimized. In this example, we only need to get three pieces of data for each teacher: name, upvote count, and downvote count, but by default the generated SQL queries all fields of the teacher table. We can use the `QuerySet`'s `only()` method to specify which attributes need to be queried, or use the `QuerySet`'s `defer()` method to specify attributes that don't need to be queried for now. This way, the generated SQL will use a projection operation to specify which columns need to be queried, thereby improving query performance, as shown below:

```Python
queryset = Teacher.objects.all().only('name', 'good_count', 'bad_count')
```

Of course, if you want to calculate the average upvote and downvote counts for each subject's teachers, you can also do this using Django's ORM framework, as shown below:

```Python
queryset = Teacher.objects.values('subject').annotate(good=Avg('good_count'), bad=Avg('bad_count'))
```

The elements in the `QuerySet` obtained here are dictionary objects, each containing three key-value pairs: `subject` representing the subject ID, `good` representing the upvote count, and `bad` representing the downvote count. If you want to get the subject name instead of the ID, you can adjust the code as follows:

```Python
queryset = Teacher.objects.values('subject__name').annotate(good=Avg('good_count'), bad=Avg('bad_count'))
```

As you can see, Django's ORM framework allows us to use object-oriented methods to complete grouping and aggregation queries in relational databases.
