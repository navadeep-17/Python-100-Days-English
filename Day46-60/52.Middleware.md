## Working with Middleware

We have already implemented the restriction that users must be logged in to vote, but a new problem arises. If our application has many features that require users to be logged in first, for example, if we also add login requirements for the previously implemented Excel report export and statistical chart viewing features, do we need to add code to check whether `userid` is in the session in every view function? The answer is no. If we did that, our view functions would inevitably be filled with large amounts of duplicate code. Programming master *Martin Fowler* once said: **Code has many bad smells, and duplication is the worst**. In Python programs, we can add extra functionality to functions through decorators; in Django projects, we can put repetitive code like verifying whether a user is logged in into **middleware**.

### Overview of Django Middleware

Middleware is a component inserted between the request and response process of a web application. It acts as an intercepting filter in the entire web application. Through middleware, we can intercept requests and responses and perform filtering on them (simply put, perform additional processing). Typically, a middleware component focuses on completing one specific task. For example, the Django framework implements session support through `SessionMiddleware` and implements session-based request authentication through `AuthenticationMiddleware`. By combining multiple middleware together, we can accomplish more complex tasks, which is exactly what the Django framework does.

The Django project configuration file includes middleware configuration, as shown below.

```Python
MIDDLEWARE = [
    'django.middleware.security.SecurityMiddleware',
    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.middleware.common.CommonMiddleware',
    'django.middleware.csrf.CsrfViewMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.contrib.messages.middleware.MessageMiddleware',
    'django.middleware.clickjacking.XFrameOptionsMiddleware',
]
```

Let's briefly explain the roles of these middleware:

1. `CommonMiddleware` - Basic settings middleware that handles the following configuration parameters.
   - DISALLOWED_USER_AGENTS - Disallowed user agents (browsers)
   - APPEND_SLASH - Whether to append `/`
   - USE_ETAG - Browser cache related
2. `SecurityMiddleware` - Security-related middleware that handles security-related configuration items.
   - SECURE_HSTS_SECONDS - Duration for forcing HTTPS
   - SECURE_HSTS_INCLUDE_SUBDOMAINS - Whether HTTPS covers subdomains
   - SECURE_CONTENT_TYPE_NOSNIFF - Whether to allow browsers to guess content types
   - SECURE_BROWSER_XSS_FILTER - Whether to enable the cross-site scripting attack filter
   - SECURE_SSL_REDIRECT - Whether to redirect to HTTPS connections
   - SECURE_REDIRECT_EXEMPT - Exemptions from HTTPS redirect
3. `SessionMiddleware` - Session middleware.
4. `CsrfViewMiddleware` - Middleware that prevents cross-site request forgery by generating tokens.
5. `XFrameOptionsMiddleware` - Middleware that prevents clickjacking attacks by setting request header parameters.

During the request process, the middleware above executes from top to bottom in the order they are written, followed by URL resolution, and finally the request reaches the view function. During the response process, the middleware above executes from bottom to top, in reverse order from the request.

### Custom Middleware

There are two ways to implement middleware in Django: class-based implementation and function-based implementation. The latter is more similar to the decorator pattern. Decorators are actually an application of the proxy pattern, placing cross-cutting concerns (functionality not inherently related to normal business logic, such as authentication, logging, encoding conversion, etc.) into proxies, where the proxy object performs the behavior of the proxied object while adding extra functionality. Middleware intercepts and filters user requests and responses while adding extra processing, which is completely consistent with decorators. Therefore, the function-based approach to implementing middleware is almost identical to writing decorators. Below, we use custom middleware to implement user login verification.

```Python
"""
middlewares.py
"""
from django.http import JsonResponse
from django.shortcuts import redirect

# Resource paths that require login to access
LOGIN_REQUIRED_URLS = {'/praise/', '/criticize/', '/excel/', '/teachers_data/'}


def check_login_middleware(get_resp):

    def wrapper(request, *args, **kwargs):
        # The requested resource path is in the set above
        if request.path in LOGIN_REQUIRED_URLS:
            # If userid is in the session, consider the user as logged in
            if 'userid' not in request.session:
                # Check if it's an Ajax request
                if request.is_ajax():
                    # Return JSON data for Ajax requests to prompt user to login
                    return JsonResponse({'code': 10003, 'hint': 'Please login first'})
                else:
                    backurl = request.get_full_path()
                    # Redirect to login page for non-Ajax requests
                    return redirect(f'/login/?backurl={backurl}')
        return get_resp(request, *args, **kwargs)

    return wrapper
```

Of course, we can also define a class to act as a decorator. If a class has the `__call__` magic method, objects of that class are callable like functions, so the following is another way to implement middleware, with the same principle as the code above.

There is also a class-based approach to implementing middleware that is no longer recommended in newer versions of Django, but you may still encounter this style of code. The general code looks like this.

```Python
from django.utils.deprecation import MiddlewareMixin


class MyMiddleware(MiddlewareMixin):

    def process_request(self, request):
        pass

    def process_view(self, request, view_func, view_args, view_kwargs):
        pass

    def process_template_response(self, request, response):
        pass

    def process_response(self, request, response):
        pass

    def process_exception(self, request, exception):
        pass
```

The five methods in the class above are all hook functions of the middleware, called when a user request is received, before entering the view function, when rendering a template, when returning a response, and when an exception occurs, respectively. Of course, whether to write these methods depends on the middleware's requirements - not all scenarios require overriding all five methods. The diagram below should help you understand this pattern.

After writing the middleware code, you need to modify the configuration file to activate the middleware.

```Python
MIDDLEWARE = [
    'django.middleware.security.SecurityMiddleware',
    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.middleware.common.CommonMiddleware',
    'django.middleware.csrf.CsrfViewMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.contrib.messages.middleware.MessageMiddleware',
    'django.middleware.clickjacking.XFrameOptionsMiddleware',
    'debug_toolbar.middleware.DebugToolbarMiddleware',
    'vote.middlewares.check_login_middleware',
]
```

Pay attention to the order of elements in this middleware list. When a request is received from a user, middleware executes in order from top to bottom. After all middleware has executed, the request finally reaches the view function. Of course, during this process, the user's request can be intercepted, just like our custom middleware above - if a user accesses a protected resource without being logged in, the middleware will redirect the request directly to the login page, and subsequent middleware and view functions will not execute. During the response process, the middleware above executes from bottom to top, allowing us to further process the response.

The execution order of middleware is very important. Middleware with dependencies must ensure that the depended-upon middleware is placed before the middleware that depends on it. For example, the middleware we just customized must be placed after `SessionMiddleware`, because we depend on the `session` object that this middleware binds to the request to determine whether the user is logged in.
