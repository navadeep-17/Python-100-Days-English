## Introduction to Front-End and Back-End Separation

In traditional web application development, most programmers consider the browser as the dividing line between front-end and back-end. The part in the browser that presents pages to users is called the front-end, while all code running on the server that provides business logic and data preparation for the front-end is collectively called the back-end. The so-called front-end and back-end separation development means that front-end and back-end engineers agree on data exchange interfaces and develop and test in parallel. The back-end only provides data and is not responsible for rendering data onto pages. The front-end retrieves data through HTTP requests and is responsible for rendering data onto pages - this work is handled by JavaScript code in the browser.

There are many benefits to using front-end and back-end separation. Below we briefly describe these benefits:

1. **Improved development efficiency**. After front-end and back-end separation, front-end and back-end code is decoupled. As long as both sides agree on the required interfaces and parameters, they can start developing in parallel without waiting for the other side's development work to finish. In this case, both front-end and back-end engineers can focus solely on their own development work, which helps build better teams. Additionally, in the front-end/back-end separation development model, even if requirements change, as long as the interfaces and data formats remain unchanged, back-end developers don't need to modify code - only the front-end needs to make changes.
2. **Enhanced code maintainability**. After separation, the application code is no longer a front-end/back-end mixture; call dependencies only exist at runtime. This makes code maintenance much easier and more pleasant, and changes won't have cascading effects throughout the system. When your code becomes clear and clean, both readability and maintainability will see qualitative improvements.
3. **Support for multiple terminals and service-oriented architecture**. After separation, the same set of data interfaces can serve different terminals, which is more conducive to building multi-terminal applications. Furthermore, since back-end interfaces can call each other through HTTP(S), this facilitates building service-oriented architectures (including microservices).

### Returning JSON Format Data

As mentioned above, in the front-end/back-end separation development model, the back-end needs to provide data interfaces for the front-end. These interfaces typically return JSON format data. In a Django project, we can first process objects into dictionaries, then use Django's `JsonResponse` to return JSON format data to the browser. The specific approach is shown below.

```Python
def show_subjects(request):
    queryset = Subject.objects.all()
    subjects = []
    for subject in queryset:
        subjects.append({
            'no': subject.no,
            'name': subject.name,
            'intro': subject.intro,
            'isHot': subject.is_hot
        })
    return JsonResponse(subjects, safe=False)
```

In the code above, we iterate through the `QuerySet` object obtained by querying subjects, process each subject's data into a dictionary, save the dictionaries in a list container named `subjects`, and finally use `JsonResponse` to serialize the list and return JSON format data to the browser. Since `JsonResponse` is serializing a list rather than a dictionary, we need to set the `safe` parameter to `False` to complete the serialization of `subjects`, otherwise a `TypeError` exception will be raised.

You may have noticed that manually converting an object to a dictionary is quite tedious, and the situation gets worse when the object has many properties or some properties are associated with complex objects. For this, we can use a third-party library called `bpmappers` to simplify the object-to-dictionary conversion. This library also provides support for the Django framework.

Install the third-party library `bpmappers`.

```Shell
pip install bpmappers
```

Write mappers (implementing object-to-dictionary conversion).

```Python
from bpmappers.djangomodel import ModelMapper

from poll2.models import Subject


class SubjectMapper(ModelMapper):

    class Meta:
        model = Subject
```

Modify the view function.

```Python
def show_subjects(request):
    queryset = Subject.objects.all()
    subjects = []
    for subject in queryset:
        subjects.append(SubjectMapper(subject).as_dict())
    return JsonResponse(subjects, safe=False)
```

Configure URL mapping.

```Python
urlpatterns = [

    path('api/subjects/', show_subjects),

]
```

### Rendering Pages with Vue.js

Next, we'll implement page rendering through the front-end framework Vue.js. If you'd like a comprehensive understanding and study of Vue.js, it's recommended to read its [official tutorial](<https://cn.vuejs.org/v2/guide/>) or search for Vue.js beginner tutorials (Vue.js Crash Course) on [YouTube](<https://www.youtube.com/>).

Rewrite the subjects.html page to use Vue.js for rendering.

```HTML
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>Subject Information</title>
    <style>
		/* Cascading style sheets omitted here */
    </style>
</head>
<body>
    <div id="container">
        <h1>All Subjects</h1>
        <hr>
        <div id="main">
            <dl v-for="subject in subjects">
                <dt>
                    <a :href="'/static/html/teachers.html?sno=' + subject.no">
                        {{ subject.name }}
                    </a>
                    <img v-if="subject.is_hot" src="/static/images/hot-icon-small.png">
                </dt>
                <dd>{{ subject.intro }}</dd>
            </dl>
        </div>
    </div>
    <script src="https://cdn.bootcdn.net/ajax/libs/vue/2.6.11/vue.min.js"></script>
    <script>
        let app = new Vue({
            el: '#main',
            data: {
                subjects: []
            },
            created() {
                fetch('/api/subjects/')
                    .then(resp => resp.json())
                    .then(json => {
                        this.subjects = json
                    })
            }
        })
    </script>
</body>
</html>
```

For front-end/back-end separation development, front-end pages need to be deployed as static resources. When the project actually goes live, we will perform static/dynamic separation for the entire web application. Static resources are deployed through Nginx or Apache servers, and Python programs that generate dynamic content are deployed on uWSGI or Gunicorn servers. Requests for dynamic content are routed from Nginx or Apache to the uWSGI or Gunicorn servers.

During the development phase, we typically use Django's built-in test server. If you want to try front-end/back-end separation, you can first place static pages in the previously created directory for static resources. For the specific approach, you can refer to the [complete project code](https://gitee.com/jackfrued/django19062).
