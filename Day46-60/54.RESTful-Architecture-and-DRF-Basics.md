## RESTful Architecture and Introduction to DRF

Turning Software, Platforms, and Infrastructure into Services is something many IT companies have been doing all along. This is what you often hear referred to as SaaS (Software as a Service), PaaS (Platform as a Service), and IaaS (Infrastructure as a Service). There are many ways to implement Service-Oriented Architecture (SOA), including RPC (Remote Procedure Call), Web Service, REST, etc. At the technical level, SOA is an **abstract, loosely coupled, coarse-grained software architecture**; at the business level, the core concepts of SOA are "**reuse**" and "**interoperability**," integrating system resources into operable, standardized services so that these resources can be recombined and applied. Among the various approaches to implementing SOA, REST is considered the most suitable architecture for internet applications. Architectures that conform to REST specifications are often referred to as RESTful architectures.

### REST Overview

The term REST was coined by **Roy Thomas Fielding** in his 2000 doctoral dissertation. Roy was the primary designer of the HTTP protocol (versions 1.0 and 1.1), the main author of the Apache server software, and the first chairman of the Apache Foundation. In his dissertation, Roy named his architectural principles for internet software REST, which stands for **RE**presentational **S**tate **T**ransfer.

The "representational" here actually refers to the "representation" of "resources." A resource is an entity on the network, or a specific piece of information on the network. It can be a piece of text, an image, a song, or a service. We can point to a resource using a URI (Uniform Resource Identifier). To obtain the resource, simply access its URI - the URI is the resource's unique identifier on the internet. Resources can have multiple external representations. The specific form in which a resource is presented is called its "representation." For example, text can be represented in `text/plain` format, `text/html` format, `text/xml` format, `application/json` format, or even binary format; images can be represented in `image/jpeg` format or `image/png` format. A URI only represents the entity of a resource, not its representation. Strictly speaking, the `.html` suffix at the end of some URLs is unnecessary because this suffix indicates format, which belongs to the "representation" category, while the URI should only represent the "location" of the resource. Its specific representation should be specified in the HTTP request header using the `Accept` and `Content-Type` fields, which are the descriptions of the "representation."

Accessing a website represents an interaction between the client and server. In this process, data and state changes are inevitably involved. Web applications typically use HTTP as their communication protocol. For the client to operate the server, it must use HTTP requests to cause "state transfers" on the server side, and this transfer is built on top of the representation layer, hence "representational state transfer." The client uses the HTTP verbs GET, POST, PUT (or PATCH), and DELETE, corresponding to four basic operations on resources: GET to retrieve a resource, POST to create a new resource (can also be used to update a resource), PUT (or PATCH) to update a resource, and DELETE to remove a resource.

Simply put, RESTful architecture is: "Each URI represents a resource, and clients operate on server-side resources through four HTTP verbs, implementing representational state transfer."

When designing web applications, if we need to provide resources to clients, we can use REST-style URIs, which is the first step in implementing RESTful architecture. Of course, a truly RESTful architecture is not just about URIs conforming to REST style - more importantly, it's about "statelessness" and "idempotency," which we will explain in later chapters. The examples below provide some REST-style URIs for reference when designing URIs.

| HTTP Method (Verb)       | URI                        | Explanation                                              |
| ------------------------ | -------------------------- | -------------------------------------------------------- |
| **GET**                  | `/students/`               | Get all students                                         |
| **POST**                 | `/students/`               | Create a new student                                     |
| **GET**                  | `/students/ID/`            | Get information for the student with the specified ID    |
| **PUT**                  | `/students/ID/`            | Update information for the specified student (full info) |
| **PATCH**                | `/students/ID/`            | Update information for the specified student (partial)   |
| **DELETE**               | `/students/ID/`            | Delete the student with the specified ID                 |
| **GET**                  | `/students/ID/friends/`    | List all friends of the student with the specified ID    |
| **DELETE**                  | `/students/ID/friends/ID/` | Delete the specified friend of the specified student     |

#### Writing Serializers

Front-end/back-end separation development requires the back-end to provide API data interfaces for the front-end and mobile clients. API interfaces typically return JSON format data, which requires serializing model objects. DRF encapsulates the `Serializer` class and `ModelSerializer` class for implementing serialization operations. By inheriting `Serializer` or `ModelSerializer`, we can define custom serializers to process objects into dictionaries, as shown below.

```Python
from rest_framework import serializers


class SubjectSerializer(serializers.ModelSerializer):

    class Meta:
        model = Subject
        fields = '__all__'
```

The code above directly inherits `ModelSerializer`, specifying the model to serialize through the `Meta` class's `model` attribute and the model fields to serialize through the `fields` attribute. We can then use this class in view functions to implement serialization of the `Subject` model.

#### Writing View Functions

The DRF framework supports two ways to implement data interfaces: FBV (Function-Based Views) and CBV (Class-Based Views). Let's first look at how to implement data interfaces using FBV, as shown below.

```Python
from rest_framework.decorators import api_view
from rest_framework.response import Response


@api_view(('GET', ))
def show_subjects(request: HttpRequest) -> HttpResponse:
    subjects = Subject.objects.all().order_by('no')
    # Create a serializer object and specify the model to serialize
    serializer = SubjectSerializer(subjects, many=True)
    # Get the dictionary corresponding to the model through the serializer's data attribute and return JSON data by creating a Response object
    return Response(serializer.data)
```

#### Implementing the Teacher Information Data Interface

Write serializers.

```Python
class SubjectSimpleSerializer(serializers.ModelSerializer):

    class Meta:
        model = Subject
        fields = ('no', 'name')


class TeacherSerializer(serializers.ModelSerializer):

    class Meta:
        model = Teacher
        exclude = ('subject', )
```

Write view functions.

```Python
@api_view(('GET', ))
def show_teachers(request: HttpRequest) -> HttpResponse:
    try:
        sno = int(request.GET.get('sno'))
        subject = Subject.objects.only('name').get(no=sno)
        teachers = Teacher.objects.filter(subject=subject).defer('subject').order_by('no')
        subject_seri = SubjectSimpleSerializer(subject)
        teacher_seri = TeacherSerializer(teachers, many=True)
        return Response({'subject': subject_seri.data, 'teachers': teacher_seri.data})
    except (TypeError, ValueError, Subject.DoesNotExist):
        return Response(status=404)
```

Configure URL mappings.

```Python
urlpatterns = [

    path('api/teachers/', show_teachers),

]
```

### User Login in Front-End/Back-End Separation

We mentioned earlier that HTTP is stateless - once a request ends, the connection is closed, and the next time the server receives a request, it doesn't know which user sent it. But for a web application, it needs state management so that the server knows where HTTP requests come from, can determine whether to allow the user's request, and can provide better service. This process is commonly known as **session management**.

Previously, we managed sessions (user tracking) like this: after the user successfully logs in, a session object saves user-related data on the server side, then the session object's ID is written to the browser's cookie. On the next request, the HTTP request header carries the cookie data, the server reads the sessionid from the cookie, and finds the corresponding session object to retrieve previously saved user data. As we mentioned earlier, REST architecture is the most suitable architecture for internet applications, and it emphasizes HTTP's statelessness, which ensures the application's horizontal scalability (when concurrent access increases, new server nodes can be added to scale the system). Obviously, session-based user tracking requires the server to save session objects, and when horizontally scaling by adding new server nodes, session objects need to be copied and synchronized, which is clearly very troublesome. There are two solutions: one is to set up a cache server (like Redis) to let multiple server nodes share the cache service and store session objects directly in the cache server; the other is to abandon session-based user tracking and use **token-based user tracking**.

Token-based user tracking generates an identity token for the user after successful login and saves it in the browser's local storage (localStorage, sessionStorage, cookie, etc.). This way, the server doesn't need to save user state, making horizontal scaling very easy. The specific flow of token-based user tracking is as follows:

1. When the user logs in, if login is successful, a token is generated for the user in a certain way. The token usually contains user identification, expiration time, and other information, and needs to be encrypted with a fingerprint generated (to prevent forging or tampering). The server returns the token to the front-end.
2. The front-end receives the token returned by the server and saves it in browser local storage (can be saved in `localStorage` or `sessionStorage`; for front-end projects using Vue.js, state management through Vuex is also possible).
3. For projects using front-end routing, each time the front-end navigates, it can first check if there's a token in `localStorage`. If not, it redirects to the login page.
4. Each request to the back-end data interface carries the token in the HTTP request header. The back-end checks whether the request header has a token. If there's no token, or if the token is invalid or expired, the server uniformly returns 401.
5. If the front-end receives an HTTP response status code of 401, it redirects to the login page.

From the description above, you've probably already realized that the most critical aspect of token-based user tracking is generating a token as the user's identity when login succeeds. There are many methods for generating tokens, and one relatively mature solution is using JSON Web Token.

#### JWT Overview

JSON Web Token is commonly abbreviated as JWT. It is an open standard (RFC 7519). With the rise of RESTful architecture, more and more projects use JWT for user authentication. A JWT is essentially three JSON objects that are encoded and combined together separated by `.`. These three JSON objects are the header, payload, and signature, as shown below.

![](res/json-web-token.png)

1. Header

    ```JSON
    {
      "alg": "HS256",
      "typ": "JWT"
    }
    ```

    The `alg` property indicates the signing algorithm, which defaults to HMAC SHA256 (abbreviated as `HS256`); the `typ` property indicates the type of this token, which is uniformly written as `JWT` in JWT.

2. Payload

    The payload section is used to store the actual data that needs to be transmitted. The JWT official documentation specifies 7 optional fields:

    - iss: Issuer
    - exp: Expiration time
    - sub: Subject
    - aud: Audience
    - nbf: Not before
    - iat: Issued at
    - jti: JWT ID

    In addition to the officially defined fields, we can add custom fields based on application needs, as shown below.

    ```JSON
    {
      "sub": "1234567890",
      "nickname": "jackfrued",
      "role": "admin"
    }
    ```

3. Signature

    The signature section generates a fingerprint for the first two parts to prevent data forgery and tampering. To create the signature, you first need to specify a secret key. This key is known only to the server and must not be leaked to users. Then, using the signing algorithm specified in the header (default is `HS256`), the signature is produced according to the following formula.

    ```Python
    HS256(base64Encode(header) + '.' + base64Encode(payload), secret)
    ```

    After computing the signature, the header, payload, and signature are concatenated into one string, with each part separated by `.`, and the JWT is ready.

#### Pros and Cons of JWT

The advantages of using JWT are very clear, including:

1. Easier to achieve horizontal scaling, because tokens are saved in the browser and the server doesn't need to manage state.
2. Better protection against CSRF attacks, because adding a token from `localStorage` or `sessionStorage` to the request header must be done through JavaScript code, rather than being automatically added to the request header.
3. Can prevent forgery and tampering, because JWTs have signatures - forged and tampered tokens cannot pass signature verification and will be identified as invalid tokens.

Of course, no technology has only advantages without disadvantages. JWT also has several drawbacks that need attention during use, specifically:

1. May be subject to XSS attacks (Cross-Site Scripting), where malicious scripts are injected to execute JavaScript code and obtain user tokens.
2. Before the token expires, there is no way to invalidate an already-issued token. To solve this problem, additional middleware and code are needed.
3. JWT is a user's identity token - once leaked, anyone can gain all permissions of that user. To reduce the risk of token theft, JWT's validity period should be set relatively short. For some important permissions, additional user authentication should be required, such as SMS verification codes.
