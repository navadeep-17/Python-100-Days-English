## RESTful Architecture and Advanced DRF

In addition to the methods discussed in the previous section, creating REST-style data interfaces with DRF can also be done through CBV (Class-Based Views). The characteristic of using CBV to create data interfaces is that the code is simple and development efficiency is high, but it's not as flexible as FBV (Function-Based Views), because with FBV, the code executed by the view function corresponding to a data interface and the data it returns are highly customizable. Below, we'll use the subject data interface as an example to explain the specific approach of creating data interfaces through CBV.

### Using CBV

#### Inheriting APIView Subclasses

Modify the previous project's `polls/views.py`, remove the `show_subjects` view function, and add a class named `SubjectView` that inherits from `ListAPIView`. `ListAPIView` can accept GET requests and encapsulates a `get` method for retrieving a data list and returning JSON data. `ListAPIView` is a subclass of `APIView`, which has many other subclasses. For example, `CreateAPIView` supports POST requests, `UpdateAPIView` supports PUT and PATCH requests, and `DestoryAPIView` supports DELETE requests. The code for `SubjectView` is shown below.

```Python
from rest_framework.generics import ListAPIView


class SubjectView(ListAPIView):
    # Specify how to retrieve subject data through queryset
    queryset = Subject.objects.all()
    # Specify how to serialize subject data through serializer_class
    serializer_class = SubjectSerializer
```

As mentioned earlier, since `SubjectView`'s parent class `ListAPIView` has already implemented the `get` method to handle GET requests for retrieving the subject list, we only need to declare how to get subject data and how to serialize subject data. The former is specified with the `queryset` attribute, and the latter with the `serializer_class` attribute. To use the above `SubjectView`, you need to modify the `urls.py` file as shown below.

```Python
urlpatterns = [
    path('api/subjects/', SubjectView.as_view()),
]
```

Obviously, the above approach is much simpler than the FBV method discussed earlier.

#### Inheriting ModelViewSet

If the subject data interface needs to support GET, POST, PUT, PATCH, and DELETE requests to support retrieving, creating, updating, and deleting subject resources, an even simpler approach is to inherit `ModelViewSet` to write the subject view class. Modify `polls/views.py` again, remove the `SubjectView` class, and add a class named `SubjectViewSet`, as shown below.

```Python
from rest_framework.viewsets import ModelViewSet


class SubjectViewSet(ModelViewSet):
    queryset = Subject.objects.all()
    serializer_class = SubjectSerializer
```

By examining the source code of the `ModelViewSet` class, we can see that it has 6 parent classes. The first 5 parent classes implement support for POST (creating subjects), GET (retrieving specific subjects), PUT/PATCH (updating subjects), DELETE (deleting subjects), and GET (retrieving subject lists) operations, corresponding to the `create`, `retrieve`, `update`, `destroy`, and `list` methods respectively. Since `ModelViewSet`'s parent classes have already implemented these methods, we can complete the entire subject data interface with almost no code. All we need to do is specify how to obtain data (via the `queryset` attribute) and how to serialize data (via the `serializer_class` attribute), which is consistent with the approach of inheriting `APIView` subclasses above.

```Python
class ModelViewSet(mixins.CreateModelMixin,
                   mixins.RetrieveModelMixin,
                   mixins.UpdateModelMixin,
                   mixins.DestroyModelMixin,
                   mixins.ListModelMixin,
                   GenericViewSet):
    """
    A viewset that provides default `create()`, `retrieve()`, `update()`,
    `partial_update()`, `destroy()` and `list()` actions.
    """
    pass
```

To use the above `SubjectViewSet`, you need to set up URL mappings in the `urls.py` file. Since `ModelViewSet` is essentially a collection of multiple view functions, unlike previous URL mapping methods, we need to first create a router and register `SubjectViewSet` through it, then add the generated URLs to the `urlpatterns` list, as shown below.

```Python
from rest_framework.routers import DefaultRouter

router = DefaultRouter()
router.register('api/subjects', SubjectViewSet)
urlpatterns += router.urls
```

Besides the `ModelViewSet` class, DRF also provides a class called `ReadOnlyModelViewSet`. As the name suggests, this class is a collection of read-only views, meaning data interfaces that inherit this class can only support GET requests - that is, requests to get individual resources and resource lists.

### Data Pagination

When using GET requests to retrieve resource lists, we typically don't load all data at once, unless the data volume is truly small. Most operations for retrieving resource lists support paginated display, meaning we can get different data by specifying page numbers (or similar identifiers) and page sizes (how many records to load at once). We can implement pagination through slicing operations on `QuerySet` objects, or use Django's `Paginator` and `Page` objects. When using DRF, you can modify `REST_FRAMEWORK` in the Django configuration file to configure default pagination classes and page sizes to implement pagination, as shown below.

```Python
REST_FRAMEWORK = {
    'PAGE_SIZE': 10,
    'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.PageNumberPagination'
}
```

Besides the `PageNumberPagination` paginator configured above, DRF also provides `LimitOffsetPagination` and `CursorPagination` paginators. Worth mentioning is `CursorPagination`, which can avoid exposing the website's data volume when using page number pagination. Interested readers can explore this on their own. If you don't want to use the default pagination settings in the configuration file, you can add a `pagination_class` attribute to the view class to re-specify the paginator. Typically, this attribute can be set to a custom paginator, as shown below.

```Python
from rest_framework.pagination import PageNumberPagination


class CustomizedPagination(PageNumberPagination):
    # Default page size
    page_size = 5
    # Query parameter for page size
    page_size_query_param = 'size'
    # Maximum page size
    max_page_size = 50
```

```Python
class SubjectView(ListAPIView):
    # Specify how to retrieve data
    queryset = Subject.objects.all()
    # Specify how to serialize data
    serializer_class = SubjectSerializer
    # Specify how to paginate
    pagination_class = CustomizedPagination
```

If you don't want data pagination, you can set the `pagination_class` attribute to `None` to disable the default paginator.

### Data Filtering

If you want to use CBV to create a data interface for getting teacher information, you can also do so by inheriting `ListAPIView`. However, since we need to get teachers for a specific subject, we need to filter teacher data rather than directly getting all teachers. If you want to get the subject ID from the request and filter teachers by it, you can do so by overriding the `get_queryset` method, as shown below.

```Python
class TeacherView(ListAPIView):
    serializer_class = TeacherSerializer

    def get_queryset(self):
        queryset = Teacher.objects.defer('subject')
        try:
            sno = self.request.GET.get('sno', '')
            queryset = queryset.filter(subject__no=sno)
            return queryset
        except ValueError:
            raise Http404('No teachers found.')
```

In addition to the above approach, you can also use the third-party library `django-filter` to work with DRF for data filtering. After using `django-filter`, you can support data filtering by configuring the `filter-backends` attribute in the view class and specifying `DjangoFilterBackend`. After completing this configuration, you can use the `filter_fields` attribute or `filterset_class` attribute to specify how to filter data. Interested readers can research this on their own.
