## Concurrent Programming in Python - 3

Crawlers are typical I/O-intensive tasks. The characteristic of I/O-intensive tasks is that the program frequently enters a blocking state due to I/O operations. For example, when we previously used `requests` to fetch page code or binary content, after sending a request, the program must wait for the website to return a response before it can continue running. If the target website is not very responsive or the network conditions are not ideal, the wait time for a response can be quite long, and during this entire process, the program is simply blocking there, doing nothing at all. Through previous lessons, we already know that multithreading can speed up crawlers. The essence of using multithreading is that when one thread is blocked, the program still has other threads that can continue running, so the entire program doesn't waste a lot of time in blocking and waiting.

In fact, there is another type of concurrent programming that is very well suited for I/O-intensive tasks, which we call asynchronous programming, or you can call it asynchronous I/O. This approach doesn't require starting multiple threads or multiple processes to achieve concurrency. Instead, it improves CPU utilization through the cooperation of multiple subroutines, solving the problem of low CPU utilization in I/O-intensive tasks. I generally refer to this approach as "cooperative concurrency." Here, I don't intend to discuss the various I/O modes of operating systems, as this is too abstract for many readers. But we need to introduce two pairs of concepts: one pair is "blocking" and "non-blocking," and the other is "synchronous" and "asynchronous."

### Basic Concepts

#### Blocking

A blocking state refers to when a program is suspended because it hasn't obtained the required computing resources. If a program cannot continue processing other things during the period it's waiting for an operation to complete, the program is said to be blocking on that operation. Blocking can happen at any time. The most typical cases are I/O interrupts (including network I/O, disk I/O, user input, etc.), sleep operations, waiting for a thread to finish execution, and even during CPU context switching, when the program cannot truly execute - this is what we call blocking.

#### Non-blocking

If a program is not blocked during the waiting process for an operation and can continue processing other things, the program is said to be non-blocking on that operation. Non-blocking cannot exist at every program level or in every situation. Only when the encapsulation level of a program can encompass independent subroutine units can non-blocking exist. Obviously, blocking on certain operations can lead to increased time consumption and reduced efficiency, so we would want to make them non-blocking.

#### Synchronous

When different program units need to coordinate through some communication method during execution to complete a task, we say these program units execute synchronously. For example, in the bank account deposit operation discussed earlier, we used "locks" as communication signals to force multiple deposit operations to execute in a queued sequential manner - this is what we call synchronous execution.

#### Asynchronous

When different program units can complete a task without needing to communicate and coordinate during execution, we call this asynchronous. For example, when using a crawler to download pages, after the scheduler calls the download program, it can immediately schedule other tasks without needing to maintain communication with the download task to coordinate behavior. The downloading and saving operations for different web pages are unrelated and don't need to notify or coordinate with each other. Obviously, the completion time and order of asynchronous operations cannot be determined.

Many people cannot accurately grasp these concepts, so let's briefly summarize: synchronous vs. asynchronous focuses on the **message communication mechanism**, ultimately manifesting as the difference between "ordered" and "unordered"; blocking vs. non-blocking focuses on **the program's state while waiting for messages**, ultimately manifesting as whether the program can do something else while waiting. If you want to deeply understand these concepts, I recommend reading the classic book [UNIX Network Programming](https://item.jd.com/11880047.html), which is an excellent resource.

### Generators and Coroutines

As mentioned earlier, asynchronous programming is a form of "cooperative concurrency" that improves CPU utilization through the cooperation of multiple subroutines, reducing time wasted in blocking and waiting, ultimately achieving the effect of concurrency. We can call these cooperating subroutines "coroutines," which are the key to implementing asynchronous programming. Before introducing coroutines, let's look at what a generator is through the code below.

```Python
def fib(max_count):
    a, b = 0, 1
    for _ in range(max_count):
        a, b = b, a + b
        yield a
```

Above, we wrote a generator that produces the Fibonacci sequence. Calling the `fib` function above does not execute the function and return a value, because there is a special keyword `yield` in the `fib` function. This keyword makes the `fib` function different from regular functions - calling it produces a generator object. We can verify this with the code below.

```Python
gen_obj = fib(20)
print(gen_obj)
```

Output:

```
<generator object fib at 0x106daee40>
```

We can use the built-in function `next` to get Fibonacci values from the generator object, or iterate over all values the generator can provide using a `for-in` loop, as shown below.

```Python
for value in gen_obj:
    print(value)
```

Once a generator is pre-activated, it becomes a coroutine that can cooperate with other subroutines.

```Python
def calc_average():
    total, counter = 0, 0
    avg_value = None
    while True:
        curr_value = yield avg_value
        total += curr_value
        counter += 1
        avg_value = total / counter


def main():
    obj = calc_average()
    # Pre-activate the generator
    obj.send(None)
    for _ in range(5):
        print(obj.send(float(input())))


if __name__ == '__main__':
    main()
```

The `main` function above first activates the generator object as a coroutine by sending a `None` value through the generator object's `send` method. The same effect can also be achieved through `next(obj)`. Then, the coroutine object receives the data sent by the `main` function and yields the average of the data. Through the example above, I wonder if you can see how the two subroutines are "cooperating."

### Async Functions

In Python 3.5, two very interesting elements were introduced: `async` and `await`, which became official keywords in Python 3.7. With these two keywords, you can simplify coroutine code writing and make multiple subroutines cooperate together in a simpler way. Let's illustrate with an example. Please look at the code below first.

```Python
import time


def display(num):
    time.sleep(1)
    print(num)


def main():
    start = time.time()
    for i in range(1, 10):
        display(i)
    end = time.time()
    print(f'{end - start:.3f} seconds')


if __name__ == '__main__':
    main()
```

The code above outputs numbers `1` through `9` in sequence on each execution, with a `1` second interval between each, and the entire code takes about `9` seconds to execute. I believe everyone can understand this. I wonder if you realize that this code executes in a synchronous and blocking manner - the synchronous aspect can be seen from the code's output, and the blocking means that when the `display` function sleeps, all other parts of the code cannot continue executing and must wait for the sleep to end.

Next, let's try to rewrite the code above using an asynchronous approach, making the `display` function operate asynchronously.

```Python
import asyncio
import time


async def display(num):
    await asyncio.sleep(1)
    print(num)


def main():
    start = time.time()
    objs = [display(i) for i in range(1, 10)]
    loop = asyncio.get_event_loop()
    loop.run_until_complete(asyncio.wait(objs))
    loop.close()
    end = time.time()
    print(f'{end - start:.3f} seconds')


if __name__ == '__main__':
    main()
```

Python's `asyncio` module provides support for asynchronous I/O. In the code above, we first added the `async` keyword before the `display` function to make it an async function. Calling an async function doesn't execute the function body but instead returns a coroutine object. We changed `time.sleep(1)` in the `display` function to `await asyncio.sleep(1)`. The difference between the two is that the latter won't cause the entire code to block, because the `await` operation gives other cooperating subroutines the opportunity to get CPU resources and run. To make these subroutines cooperate, we need to place them on an event loop (a system that implements message dispatching and delivery), because **when a coroutine encounters an I/O operation that blocks, it goes to the event loop to monitor whether the I/O operation is complete, registers its context and its wakeup function (to resume execution), and then the coroutine enters a blocked state**. Line 12 of the code above creates `9` coroutine objects and puts them in a list. Line 13 gets the system's event loop through the `asyncio` module's `get_event_loop` function. Line 14 mounts the coroutine objects onto the event loop through the `asyncio` module's `run_until_complete` function. Running the code above, you'll find that the `9` coroutines that each block for `1` second only block for about `1` second in total, because **a blocked coroutine object gives up CPU ownership rather than leaving the CPU idle, which greatly improves CPU utilization**. We'll also notice that the numbers are not printed in order from `1` to `9`, which is exactly the result we want, indicating that they are **executing asynchronously**. For I/O-intensive tasks like crawlers, this cooperative concurrency is a better choice than using multithreading in many scenarios, because this approach reduces the overhead of managing and maintaining multiple threads and thread context switching.

### The aiohttp Library

The `requests` third-party library we used before does not support asynchronous I/O. If you want to use asynchronous I/O to speed up crawler code execution, you can install and use the third-party library called `aiohttp`.

The code below uses `aiohttp` to scrape the homepages of `10` websites and parse their titles.

```Python
import asyncio
import re

import aiohttp
from aiohttp import ClientSession

TITLE_PATTERN = re.compile(r'<title.*?>(.*?)</title>', re.DOTALL)


async def fetch_page_title(url):
    async with aiohttp.ClientSession(headers={
        'User-Agent': 'Mozilla/5.0 (Macintosh; Intel Mac OS X 10_14_6) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/95.0.4638.69 Safari/537.36',
    }) as session:  # type: ClientSession
        async with session.get(url, ssl=False) as resp:
            if resp.status == 200:
                html_code = await resp.text()
                matcher = TITLE_PATTERN.search(html_code)
                title = matcher.group(1).strip()
                print(title)


def main():
    urls = [
        'https://www.python.org/',
        'https://www.jd.com/',
        'https://www.baidu.com/',
        'https://www.taobao.com/',
        'https://git-scm.com/',
        'https://www.sohu.com/',
        'https://gitee.com/',
        'https://www.amazon.com/',
        'https://www.usa.gov/',
        'https://www.nasa.gov/'
    ]
    objs = [fetch_page_title(url) for url in urls]
    loop = asyncio.get_event_loop()
    loop.run_until_complete(asyncio.wait(objs))
    loop.close()


if __name__ == '__main__':
    main()
```

Output:

```
京东(JD.COM)-正品低价、品质保障、配送及时、轻松购物！
搜狐
淘宝网 - 淘！我喜欢
百度一下，你就知道
Gitee - 基于 Git 的代码托管和研发协作平台
Git
NASA
Official Guide to Government Information and Services   &#124; USAGov
Amazon.com. Spend less. Smile more.
Welcome to Python.org
```

From the output above, we can see that the output order of website homepage titles has no relation to the order of their URLs in the list. Lines 11 through 13 of the code create a `ClientSession` object, whose `get` method can send a request to a specified URL, as shown in line 14. This is essentially no different from the `Session` object in `requests`, with the only difference being that asynchronous context is used here. The `await` on line 16 allows subroutines blocked by I/O operations to give up CPU ownership, enabling other subroutines to run and scrape pages. Lines 17 and 18 use regular expression capture group operations to parse the web page title. `fetch_page_title` is an async function decorated with the `async` keyword, and calling it returns a coroutine object, as shown on line 35. The rest of the code is no different from the previous example, and I believe everyone can understand it.

You can try switching `aiohttp` back to `requests` to see what the difference is compared to the code above when not using asynchronous I/O or multithreading. I believe this comparison will help you gain a deeper understanding of the concepts we emphasized earlier: synchronous and asynchronous, blocking and non-blocking.
