## MySQL Performance Optimization

### Basic Principles

To achieve the best performance from MySQL, you need to follow 3 basic usage principles.

1. Let MySQL return to its fundamental role of storage: Use MySQL database only for data storage, not for complex data computation or carrying business logic, ensuring the separation of storage and computation.
2. When querying data, try to use single-table queries and reduce cross-database queries and multi-table joins.
3. Eliminate large transactions, large SQL statements, large batches, large fields, and other performance killers.
    - Large transactions: Involve many steps and multiple tables and fields, which can easily cause resource contention and even deadlocks. Once a transaction is rolled back, resources will be occupied for too long.
    - Large SQL: Complex SQL means too many table joins. When MySQL processes SQL involving more than 3 tables, it consumes excessive resources and performs poorly.
    - Large batches: Executing multiple SQL statements at once can reduce the overhead of executing them one by one, but thorough testing must be ensured, and execution should be during off-peak business hours or non-business hours.
    - Large fields: blob and text type large fields should be used as sparingly as possible. When they must be used, try to separate them from the main business table to reduce retrieval and updates of these fields.

### Database and Table Creation

1. The default storage engine must be specified as InnoDB, and MyISAM storage engine should be disabled. With the release of MySQL 8.0, all data dictionary tables have been converted to InnoDB, and the MyISAM storage engine has become history.
2. Default character set should be UTF8mb4. The UTF8 in previous versions was actually UTF8mb3, which did not include certain special characters. The new UTF8mb4 includes all characters, and the official recommendation is strongly to use this character set.
3. Disable case sensitivity. Set the `lower_case_table_names` parameter to `1` to disable case sensitivity, meaning uppercase T and lowercase t are treated the same.
4. Features like stored procedures, triggers, views, and events should be implemented in the application code as much as possible. On one hand, this is for separating storage and computation; on the other hand, these features are very incomplete, and debugging, troubleshooting, and monitoring are very difficult. Related data dictionaries are also incomplete, posing potential risks. Generally, they are prohibited in production databases.
5. Keep the number of tables in a single database instance under 2000.

#### InnoDB Table Considerations

1. Primary key columns should use `unsigned` integers. `auto_increment` can be used, but manual updates to primary keys should be prohibited.
2. Every column must have a `comment` annotation.
3. The `engine` must be explicitly specified when creating tables.
4. Three mandatory fields for every table: `xxx_id`, `xxx_create`, `xxx_modified`. Where `xxx_id` is the primary key with `unsigned` integer type (e.g., `int unsigned`); both `xxx_create` and `xxx_modified` are of `datetime` type, recording the creation time and modification time of each record respectively.
5. All fields must specify `not null`, with `default` values for empty values, because MySQL has difficulty optimizing `null` values. Composite indexes containing `null` values will be invalidated, ultimately leading to low query efficiency.
6. Try to keep the number of fields in a single table within 50. If there are too many fields, consider vertical splitting.
7. Disable `enum` and `set` types, as they have poor compatibility and performance.
8. Large files should not use the `blob` type but rather store their paths. Types like `blob` and `text` cause performance degradation and greatly increase the cost of full table scans.
9. For data sensitive to precision such as currency, use fixed-point numbers (`decimal`) instead of floating-point numbers (`float`).
10. Do not use `char(15)` to store IP addresses; use `int unsigned` instead. You can use the `inet_aton` and `inet_ntoa` functions to convert between integers and IP addresses.

### Using Indexes

In the previous article ["Relational Database MySQL"](../Day36-40/36-38.关系型数据库MySQL.md), we already covered index-related knowledge. Here we provide a brief review.

#### Index Design Principles

1. The columns for creating indexes are not necessarily the columns to be queried in `select` operations. The most suitable columns for indexing are those that appear in `where` clauses as filtering conditions or in join clauses as table join conditions.
2. Columns with uniqueness have good index performance; columns with many duplicate values have poor index performance.
3. If creating an index for a string type, it's best to specify a prefix length to create a short index. Short indexes can reduce disk I/O and perform better during comparisons. More importantly, MySQL's underlying high-speed index cache can cache more key values.
4. When creating a composite index (multi-column index) containing N columns, it is equivalent to creating N indexes. At this point, you should use leftmost prefix matching.
5. Do not overuse indexes. More indexes are not always better. Indexes require extra storage space and affect write operation performance (indexes also need to be updated when inserting, deleting, or updating data). MySQL needs to consider the use of each index when generating execution plans, which also takes time.
6. Be aware of scenarios that may invalidate indexes, such as: fuzzy queries using leading wildcards, queries using negative conditions, etc.

### Using Procedures

Procedures, commonly known as stored procedures, are pre-compiled collections of SQL statements stored in the database. Calling stored procedures can simplify the work of application developers, reduce communication with the database server, and help improve data operation performance. These were already mentioned in the previous article ["Relational Database MySQL"](../Day36-40/36-38.关系型数据库MySQL.md).

### Data Partitioning

MySQL supports data partitioning. Through partitioning, you can store more data, optimize queries, achieve greater throughput, and quickly delete expired data. For this topic, it is recommended to refer to MySQL's [official documentation](https://dev.mysql.com/doc/refman/5.7/en/partitioning-overview.html). Data partitioning has the following types:

1. RANGE partitioning: Distributes data to different partitions based on continuous interval ranges.

   ```SQL
   CREATE TABLE tb_emp (
       eno INT NOT NULL,
       ename VARCHAR(20) NOT NULL,
       job VARCHAR(10) NOT NULL,
       hiredate DATE NOT NULL,
       dno INT NOT NULL
   )
   PARTITION BY RANGE( YEAR(hiredate) ) (
       PARTITION p0 VALUES LESS THAN (1960),
       PARTITION p1 VALUES LESS THAN (1970),
       PARTITION p2 VALUES LESS THAN (1980),
       PARTITION p3 VALUES LESS THAN (1990),
       PARTITION p4 VALUES LESS THAN MAXVALUE
   );
   ```

2. LIST partitioning: Distributes data to different partitions based on enumeration value ranges.

3. HASH partitioning / KEY partitioning: Distributes data to different partitions based on the number of partitions.

   ```SQL
   CREATE TABLE tb_emp (
       eno INT NOT NULL,
       ename VARCHAR(20) NOT NULL,
       job VARCHAR(10) NOT NULL,
       hiredate DATE NOT NULL,
       dno INT NOT NULL
   )
   PARTITION BY HASH(dno)
   PARTITIONS 4;
   ```

### SQL Optimization

1. Locating inefficient SQL statements - Slow query log.

   - View slow query log related configuration

      ```SQL
      mysql> show variables like 'slow_query%';
      +---------------------------+----------------------------------+
      | Variable_name             | Value                            |
      +---------------------------+----------------------------------+
      | slow_query_log            | OFF                              |
      | slow_query_log_file       | /mysql/data/localhost-slow.log   |
      +---------------------------+----------------------------------+

      mysql> show variables like 'long_query_time';
      +-----------------+-----------+
      | Variable_name   | Value     |
      +-----------------+-----------+
      | long_query_time | 10.000000 |
      +-----------------+-----------+
      ```

   - Create the slow query log file and change its owner.

      ```Bash
      touch /var/log/mysqld-slow.log
      chown mysql /var/log/mysqld-slow.log
      ```

   - Modify the global slow query log configuration.

      ```SQL
      mysql> set global slow_query_log_file='/var/log/mysqld-slow.log'
      mysql> set global slow_query_log='ON';
      mysql> set global long_query_time=1;
      ```

   - Or directly modify the MySQL configuration file to enable the slow query log.

      ```INI
      [mysqld]
      slow_query_log=ON
      slow_query_log_file=/var/log/mysqld-slow.log
      long_query_time=1
      ```

   > **Note**: After modifying the configuration file, MySQL needs to be restarted. The corresponding command on CentOS is `systemctl restart mysqld`.

2. Use `explain` to understand the SQL execution plan. For example:

   ```SQL
   explain select ename, job, sal from tb_emp where dno=20\G
   *************************** 1. row ***************************
              id: 1
     select_type: SIMPLE
           table: tb_emp
            type: ref
   possible_keys: fk_emp_dno
             key: fk_emp_dno
         key_len: 5
             ref: const
            rows: 7
           Extra: NULL
   1 row in set (0.00 sec)
   ```

   - `select_type`: Query type (SIMPLE - simple query, PRIMARY - main query, UNION - union, SUBQUERY - subquery).
   - `table`: The table of the output result set.
   - `type`: Access type (ALL - full table scan with worst performance, index, range, ref, eq_ref, const, NULL).
   - `possible_keys`: Indexes that might be used during the query.
   - `key`: The index actually used.
   - `key_len`: The length of the index field.
   - `rows`: The number of rows scanned. Fewer rows definitely means better performance.
   - `extra`: Additional information.

3. Analyze SQL using `show profiles` and `show profile for query`.

   Starting from MySQL 5.0.37, the profiling system is supported to help users understand the details of SQL execution performance. You can check whether MySQL supports and has enabled the profiling system using the following methods.

   ```SQL
   select @@have_profiling;
   select @@profiling;
   ```

   If the profiling system is not enabled, you can turn it on with the following SQL.

   set profiling=1;

4. Optimizing CRUD operations.

   - Optimizing `insert` statements
     - Following an `insert` statement with multiple value groups for batch insertion performs better than separate `insert` statements.
     - If multiple connections are inserting data into the same table, using `insert delayed` can achieve better performance.
     - When loading data from a text file into a table, using `load data infile` performs much better than `insert`.

   - Optimizing `order by` statements

     - If the `where` clause conditions and `order by` clause conditions are the same, the sort order matches the index order, and all sort fields are either ascending or descending, then the index alone can complete the sorting.

   - Optimizing `group by` statements

     - When using the `group by` clause for grouping, if you want to avoid the overhead of sorting, you can use `order by null` to disable sorting.

   - Optimizing nested queries

     - Starting from MySQL 4.1, nested queries (subqueries) are supported, allowing the result of one query to be used as part of another query. In some cases, subqueries can be replaced by more efficient join queries, because MySQL does not need to create temporary tables in memory to complete the logically multi-step query during join queries.

   - Optimizing OR conditions

     - If conditions are connected by `or`, indexes will only be effective when all conditions use indexes.

   - Optimizing pagination queries

     - A common headache with pagination queries is something like `limit 1000, 20`, where MySQL has already sorted the first 1020 records but only returns records 1001 through 1020. The first 1000 records are actually useless, and the query and sorting cost is very high. A common optimization approach is to complete the sorting and pagination on the index, then perform table join operations based on the returned results to get the final result. This avoids full table scans and external sorting.

       ```SQL
       select * from tb_emp order by ename limit 10000, 20;
       select * from tb_emp t1 inner join (select eno from tb_emp order by ename limit 10000, 20) t2 on t1.eno=t2.eno;
       ```

       In the code above, the 2nd line SQL is better than the 1st line SQL. Of course, the premise is that an index has already been created on the `ename` field.

   - Using SQL hints
     - USE INDEX: Suggest MySQL use the specified index.
     - IGNORE INDEX: Suggest MySQL ignore the specified index.
     - FORCE INDEX: Force MySQL to use the specified index.

### Configuration Optimization

You can use the following commands to view the default values of MySQL server configuration parameters.

```SQL
show variables;
show variables like 'key_%';
show variables like '%cache%';
show variables like 'innodb_buffer_pool_size';
```

The following commands can help you understand the MySQL server runtime status values.

```SQL
show status;
show status like 'com_%';
show status like 'innodb_%';
show status like 'connections';
show status like 'slow_queries';
```

1. Adjust `max_connections`: The maximum number of MySQL connections, default is 151. On Linux systems, if there is sufficient memory and user wait response time is not a concern, MySQL can theoretically support up to tens of thousands of connections, but this value is generally recommended to be kept under 1000.
2. Adjust `back_log`: The TCP connection backlog queue size, usually one-fifth of max_connections, with a maximum of 900.
3. Adjust `table_open_cache`: This value should be set to N times max_connections, where N represents the maximum number of tables opened per connection during queries.
4. Adjust `innodb_lock_wait_timeout`: This parameter controls the time InnoDB transactions wait for row locks. The default is 50ms. For applications requiring fast response, this value can be reduced to avoid long-hanging transactions; for background tasks, this value can be increased to avoid large rollback operations.
5. Adjust `innodb_buffer_pool_size`: The memory buffer size for InnoDB data and indexes, in bytes. The higher this value is set, the less disk I/O is needed to access table data. If possible, this value can even be set to 80% of physical memory.

### Architecture Optimization

1. Improve table access efficiency through splitting.
   - Vertical splitting
   - Horizontal splitting

2. Denormalization. The degree of standardization in database table design is called Normal Form. To increase the level of normalization, large tables usually need to be split into smaller tables. The higher the normalization level, the less data redundancy, and the likelihood of problems during insert, delete, and update operations is significantly reduced. However, saving space means queries may take more time, as single-table queries may become join queries. For this reason, in practice, we often perform denormalization operations, deliberately lowering the normalization level to add redundancy and reduce query time overhead.
   - 1NF: Columns cannot be further split
   - 2NF: All attributes depend on the primary key
   - 3NF: All attributes directly depend on the primary key (eliminating transitive dependencies)
   - BCNF: Eliminating non-trivial multi-valued dependencies

3. Use intermediate tables to improve statistical query speed.

   Use statements like `insert into intermediate_table select ... where ...` to first filter the needed data into an intermediate table, then perform statistics on the intermediate table, avoiding unnecessary computation and processing.
