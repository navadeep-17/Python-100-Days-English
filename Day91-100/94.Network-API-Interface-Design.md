## Network API Interface Design

Currently, many web applications and mobile applications use a front-end and back-end separation development model. Simply put, front-end or mobile-end separation means that the front-end or mobile client interacts with the back-end through network API interfaces, obtains the data provided by the interfaces, and is responsible for rendering the user interface. API is the abbreviation for Application Programming Interface. A network API typically refers to a resource accessible through a URL (Uniform Resource Locator), meaning that through this URL we can request the server to operate on a certain resource and return the result. Think about it - isn't a network API interface also a form of encapsulation? Simply put, it hides complex business logic behind a simple API interface.

The general format of a URL is as follows:

```
protocol://username:password@host:port/path1/.../pathN/resource-name
```

> **Note**: The username (which may not be required), password (which may not be required), port (which may use the default port), and path (the resource may be located directly under the root path `/`) in a URL are not mandatory parts and can be set as needed.

Network APIs are usually accessed based on HTTP or HTTPS. The biggest advantage of being based on HTTP/HTTPS is that access is very simple and convenient, and it enables cross-language and cross-application access and interoperability.

### Design Principles

#### Key Issues

When designing network API interfaces for mobile or PC clients, a very important principle is: **Design API interfaces based on business entities rather than user interfaces or operations**. If API interfaces are designed based on user operations or interface features, as requirements change, the user interface will also be adjusted, and the required data will change. This means back-end developers will have to constantly adjust APIs, or design multiple versions for a single API, all of which increase project development and maintenance costs. We can think of business entities as resources provided by the server, and URLs as resource locators (identifiers). This approach is the simplest and most natural. For relatively complex user operations, we can provide a "facade" (the "Facade Pattern" in design patterns) to assemble the functionality of multiple interfaces.

Below is the open API of a certain website. You can see that the API design is centered around business entities, and they are all self-descriptive.

| Comments          |                                    |
| ----------------- | ---------------------------------- |
| comments/show     | Get the comment list for a post    |
| comments/by_me    | My comment list                    |
| comments/to_me    | Comments received                  |
| comments/mentions | Comments that @mentioned me        |
| comments/create   | Create a comment                   |
| comments/destroy  | Delete a comment                   |
| comments/reply    | Reply to a comment                 |

It should be noted that **the above API interfaces are not REST-style**. REST is a network application architecture style considered most suitable for distributed network applications. For more about REST, you can read Ruan Yifeng's ["Understanding RESTful Architecture"](http://www.ruanyifeng.com/blog/2011/09/restful.html) and ["RESTful API Design Guide"](http://www.ruanyifeng.com/blog/2014/05/restful_api.html), though you should read these two articles critically, as the views expressed are not entirely correct, and some content is even self-contradictory.

API interface return data is usually in **JSON** or **XML** format. XML as a data format has basically been deprecated. For JSON format data, we should avoid returning null values, as improper handling could cause unnecessary trouble for front-end and mobile development (because developers may use strongly typed languages). To solve this problem, we can start from the source - when designing the database, try to add "not null" constraints or set reasonable default constraints for each field.

#### Other Issues

1. Update notification: Design an API that must be accessed first every time the system is used. This API will return system update information to the mobile client, allowing users to be prompted to update the App.
2. Version upgrade: When upgrading API versions, backward compatibility with lower versions should be considered, and both new and old versions should remain accessible. Version information can be included in the URL or placed in the HTTP(S) protocol header. There is much debate about this issue; interested readers can check the discussion on [Stack Overflow](https://stackoverflow.com/questions/972226/how-to-version-rest-uris).
3. Image size: The mobile client may need different sizes of an image. The size parameter can be passed when fetching images to get the corresponding resource; a better approach is to directly use cloud storage or CDN (which provides image scaling functionality), which can also accelerate resource access.

### Documentation Writing

Below, using the design of a comment interface as an example, we briefly explain how to write interface documentation.

First, we can define global return status codes.

| Return Code | Return Message           | Description                                              |
| ----------- | ------------------------ | -------------------------------------------------------- |
| 10000       | Comments retrieved successfully |                                                    |
| 10001       | Comment created successfully |                                                       |
| 10002       | Unable to create comment | Comment cannot be created due to content moderation violation |
| 10003       | Comment has been deleted | Comment was deleted due to inappropriate content when viewing |
| 10004       | ......                   | ......                                                   |

1. Get article comments.

   **GET** `/articles/{article-id}/comments/`

   Developer: Wang Dachui

   Last updated: August 10, 2018

   Tag: v 1.0

   Interface description: Get all comments for a specified article

   Usage help: Returns 20 records by default, an identity key must be set in the request header

   Request parameters:

   | Parameter | Type    | Required | Location        | Description                                     |
   | --------- | ------- | -------- | --------------- | ----------------------------------------------- |
   | page      | Integer | No       | Query parameter | Page number, default 1                          |
   | size      | Integer | No       | Query parameter | Number of comments per request (10~100), default 20 |
   | key       | String  | Yes      | Request header  | User identity token                             |

   Response:

   ```JSON
   {
       "code": 10000,
       "message": "Comments retrieved successfully",
       "page": 1,
       "size": 10,
       "totalPage": 35,
       "contents": [
           {
               "userId": 1700095,
               "nickname": "Wang Dachui",
               "pubDate": "July 31, 2018",
               "content": "Is the editor sick or something",
               /* ... */
           },
           {
           	"userId", 1995322,
               "nickname": "Bai Yuanfang",
               "pubDate": "August 2, 2018",
               "content": "Well said above",
               /* ... */
           }
       ]
       /* ... */
   }
   ```

2. Create article comment.

   **POST** `/articles/{article-id}/comments`

   Developer: Wang Dachui

   Last updated: August 10, 2018

   Tag: v 1.0

   Interface description: Create a comment for a specified article

   Usage help: None

   Request parameters:

   | Parameter | Type   | Required | Location       | Description     |
   | --------- | ------ | -------- | -------------- | --------------- |
   | userId    | String | Yes      | Request body   | User ID         |
   | key       | String | Yes      | Request header | User token      |
   | content   | String | Yes      | Request body   | Comment content |

   Response:

   ```JSON
   {
       "code": 10001,
       "message": "Comment created successfully",
       "comment": {
           "pubDate": "July 31, 2018",
           "content": "Is the editor sick or something"
           /* ... */
       }
       /* ... */
   }
   ```



> **Tip**: If you don't have experience writing interface documentation, you can use online interface documentation editing platforms like [RAP2](<http://rap2.taobao.org/>) or [YAPI](<http://yapi.demo.qunar.com/>) to write interface documentation.
